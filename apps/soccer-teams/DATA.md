# Soccer Teams data

The data layer for the "which city does this club play in?" flashcards. Everything
here is generated by the scripts in `scripts/` and checked by
`src/data/teams.test.js` (`npm test`).

| File | What it is | Built by |
| --- | --- | --- |
| `src/data/teams.json` | 40 clubs: 20 La Liga + 20 Serie A, 2026-27 season | `scripts/build-teams.mjs` (club list in `scripts/clubs.mjs`) |
| `public/logos/<slug>.svg\|png` | Club crests (see `LOGOS.md`) | `scripts/fetch-logos.mjs` |
| `src/data/maps.json` | Pre-projected SVG outlines of Spain and Italy | `scripts/build-maps.mjs` |
| `src/lib/projection.js` | `project(country, lat, lon) -> {x, y}` plus the projection parameters | hand-written, shared by the UI and `build-maps.mjs` |

To regenerate (Node 20+, no extra dependencies, needs network access):

```bash
node scripts/fetch-logos.mjs   # crests + LOGOS.md (run first: build-teams checks which logos exist)
node scripts/build-teams.mjs   # teams.json
node scripts/build-maps.mjs    # maps.json (or: --input ne_10m_admin_0_countries.geojson)
npm test
node scripts/render-preview.mjs /tmp   # optional: preview SVGs with every team dot
```

All network scripts send `User-Agent: tim-learning-sandbox/1.0 (accounts@galebach.com)`,
make sequential requests about 1 s apart, and back off on 429/5xx (honouring
`Retry-After`). See `scripts/http.mjs`.

## `teams.json` schema

```jsonc
{
  "slug": "real-madrid",          // unique, kebab-case; also the logo file name
  "name": "Real Madrid",          // common English name
  "shortName": "Real Madrid",     // compact label
  "country": "Spain",             // "Spain" | "Italy"
  "league": "La Liga",            // "La Liga" | "Serie A"
  "city": "Madrid",               // English name of the municipality the stadium is in (the quiz answer)
  "cityPopulation": 3506730,      // municipal population (integer)
  "populationYear": 2025,
  "populationSource": "INE Padrón municipal, 1 Jan 2025 (via Wikidata Q2807 P1082)",
  "lat": 40.45306, "lon": -3.68835, // stadium coordinates (WGS84)
  "logo": "logos/real-madrid.svg"   // path relative to public/, or null (UI shows an initials badge)
}
```

The order is La Liga then Serie A, alphabetical by slug within each league.

## Population

The year is the same for both countries: **1 January 2025**.

- **Spain**: INE *Padrón municipal* 2025, read from Wikidata `P1082` (population)
  statements dated 2025 whose reference is "stated in" `Q137426716` ("Municipal
  Register of Spain of 2025"). The script fails if a city lacks exactly one such statement.
- **Italy**: ISTAT, *Popolazione residente al 1° gennaio 2025* (POSAS dataset,
  `https://demo.istat.it/data/posas/POSAS_2025_it_Comuni.zip`), the all-ages total
  row for each comune, matched by ISTAT code (Wikidata `P635`). Wikidata's Italian
  population values mix 1 Jan 2023 and 1 Jan 2025 (for example, Cagliari has only
  2025), so ISTAT is read directly to keep one source and one year. Where Wikidata
  has a 2025 ISTAT value, it agrees (Cagliari: 146,692).

Populations are for the municipality (*municipio* / *comune*), not the metro area.
That's why Cornellà de Llobregat (92k) is small next to Barcelona, and Venice
(249k) includes mainland Mestre.

## Stadium coordinates

`lat`/`lon` is the Wikidata `P625` coordinate of the stadium the club uses in
2026-27, as listed in the season article's stadium table (resolved from the linked
en.wikipedia article to its Wikidata item), rounded to 5 decimals. Clubs that share
a stadium have identical coordinates (Inter and Milan at San Siro, Lazio and Roma at
the Stadio Olimpico).

## City judgment calls

The rule: **`city` is the municipality where the club's stadium physically is**,
with the English name an English speaker would expect.

- **Espanyol → Cornellà de Llobregat.** Espanyol is a Barcelona club by name and
  history, but since 2009 it has played at the RCDE Stadium, which lies in Cornellà de
  Llobregat (the stadium straddles the border with El Prat de Llobregat; Wikipedia and
  the club give Cornellà). This follows the same rule as Getafe and Villarreal, which
  are separate municipalities from Madrid and Valencia. If the quiz should accept
  "Barcelona", that has to be handled in the UI; the data keeps the physical location.
- **Sassuolo → Reggio Emilia.** The club is from the town of Sassuolo but plays at the
  Mapei Stadium – Città del Tricolore in Reggio Emilia (about 20 km away). Same rule.
- **Levante → Valencia.** The Estadi Ciutat de València is in the city of Valencia, so
  Levante and Valencia CF share an answer.
- **Rayo Vallecano → Madrid** (Vallecas Stadium, in Madrid's Puente de Vallecas
  district). Early in 2026-27 Rayo played at the Estadio Butarque in Leganés while
  Vallecas was closed. The ban was lifted on 14 Sep 2026, so the home ground and the
  coordinates are Vallecas.
- **Real Betis → Seville.** Betis is temporarily at the Estadio de La Cartuja (also in
  Seville) while the Benito Villamarín is rebuilt. The coordinates are La Cartuja's, the
  venue the season article lists. The city is Seville either way.
- **Getafe → Getafe**, **Villarreal → Villarreal** (the town's official Valencian name
  is Vila-real; we use the club's and English usage), **Monza → Monza** (not Milan),
  **Atalanta → Bergamo**.
- **Athletic Club → Bilbao.** `name` is "Athletic Club" (the official name, which the
  brief uses). English Wikipedia titles the club "Athletic Bilbao".
- **Real Sociedad → San Sebastián** (Basque: Donostia), **Alavés → Vitoria-Gasteiz**
  (the official bilingual name, which English sources also use).
- **Deportivo → A Coruña.** The city name is the official Galician form, which English
  Wikipedia uses. The club's `name` is "Deportivo de La Coruña", its common English name.
- **Juventus and Torino → Turin**, **Lazio and Roma → Rome**, **Inter and Milan → Milan**,
  **Napoli → Naples**, **Fiorentina → Florence**, **Genoa → Genoa**, **Venezia → Venice**:
  the English exonyms.
- **Racing Santander → Santander.**

Many club names contain their city (Real Madrid, Celta Vigo, Elche, ...). That's how
the clubs are named, so it's left as is. The UI can decide whether to hide names on
the question side.

## Maps (`maps.json` + `projection.js`)

- **Source:** Natural Earth 1:10m Cultural Vectors, *Admin 0 – Countries*
  (`ne_10m_admin_0_countries.geojson` from the
  [natural-earth-vector](https://github.com/nvkelso/natural-earth-vector) repo, tag
  `v5.1.2`). Natural Earth is **public domain**. The 1:10m scale was chosen over 1:50m
  so the coastal stadiums (Riazor, Balaídos, Anoeta, Sardinero, Unipol Domus, ...)
  fall inside the outline. After simplification the file is still small.
- **Projection:** equirectangular with cos(lat0) scaling, at 60 SVG units per degree of
  latitude. `x = frame.x + (lon − lonMin)·cos(lat0)·60`, `y = frame.y + (latMax − lat)·60`.
  - Spain mainland + Balearics: lon −9.6…4.6, lat 35.7…44.0, lat0 = 40.
  - Canary Islands inset: lon −18.4…−13.2, lat 27.4…29.5, lat0 = 28.5, drawn at the
    same scale in a box at (6, 506), 274×126, below Andalusia. `project('Spain', lat, lon)`
    sends any point with lat < 30 into the inset. A test checks that Las Palmas'
    stadium lands on Gran Canaria.
  - Italy: lon 6.4…18.8, lat 35.3…47.3, lat0 = 42 (Lampedusa included).
  - Mallorca, Menorca, Ibiza, Formentera, Sicily, Sardinia, Elba and the other larger
    islands are drawn in position.
- **Simplification:** Douglas-Peucker in projected units (tolerance 0.3 units, about
  0.5 km). Islets under 1 square unit (about 2.5 km²) are dropped, which removes Alicudi
  and Ventotene in Italy. Polygon holes are dropped, so San Marino and Vatican City
  are filled in as part of Italy. Coordinates are rounded to 0.1 unit.
- **Not drawn:** Spain's North African territories (Ceuta, Melilla, Alborán and the
  *plazas de soberanía*), because they would float next to an undrawn Morocco.
- **Format:** `maps.json` has `{ meta, Spain, Italy }`. Each country is
  `{ viewBox, width, height, paths: [{ id, d }], insets: [{ id, name, x, y, width, height }] }`.
  `paths[].id` is `"main"` or the inset id (`"canary-islands"`). `d` is absolute
  `M x,y x,y … Z` rings. Draw the inset rects as border boxes.
- **Size:** `maps.json` is about 32 KB (Spain about 14.5k path characters, Italy about 17k).
- **Known limitation:** Venezia's Stadio Penzo, on Sant'Elena at the eastern tip of
  Venice, is about 0.7 km beyond the 1:10m Venice island polygon. On the map the dot
  sits right on the lagoon shore. The outline test allows that one club up to 0.75 units
  (about 1.3 km) from the outline. Every other club is strictly inside.

## Card order and stats (`src/lib/deck.js`, `history.js`, `sync.js`)

Not data, but it lives next to it. There are no rounds: every card is drawn from
the teams in the current country filter. Teams that are due for review come
first; teams Tim has never missed wait 30+ days. The same team never comes up
twice in a row (unless the filter has only one team). See "Schedule" below.

### Where the stats live

- **Server (source of truth):** `apps/soccer-teams/data/stats.json` (on the prod
  box: `/root/pkg/tim-learning-sandbox/apps/soccer-teams/data/stats.json`). One shared
  file; the app is single-user. It is gitignored and untracked, and `scripts/deploy.sh`
  only cleans `apps/*/dist`, so `git pull --ff-only` and deploys leave it alone
  (`server/soccer_teams_stats.test.js` checks this).
- **Browser:** localStorage keeps a full copy of the history
  (`soccer-teams:events:v2`), a queue of answers not yet confirmed by the server
  (`soccer-teams:pending:v2`) and a random device id (`soccer-teams:device`).

File format:

```jsonc
{
  "version": 2,
  "updatedAt": "2026-10-16T20:00:00.000Z",
  "teams": {                     // derived from events, for reading; rebuilt on every write
    "roma": { "slug": "roma", "attempts": 3, "misses": 2, "gots": 1,
              "lastSeenAt": "...", "lastWrongAt": "...", "lastGotAt": "...",
              "recent": ["m", "m", "g"],   // last 10 answers
              "streak": 1 }                   // "Got it" in a row since the last miss
  },
  "events": [                    // the truth: every answer, append-only
    { "id": "dk3j2...-mg1x2a-4", "slug": "roma", "at": "...", "got": false },
    // one-time import of the old per-browser v1 stats:
    { "id": "baseline-<device>-roma", "kind": "baseline", "slug": "roma", "at": "...",
      "attempts": 3, "misses": 2, "gots": 1, "recent": ["m", "m", "g"] }
  ]
}
```

### Sync and merging

Each answer is an event with a unique id (device id + time + counter). Merging is
a **union of events by id**, then the per-team stats are re-derived (events sorted
by time, then id). That is idempotent and order-independent, so two devices can
answer offline at the same time and nothing is lost.

- Answers go into the local cache and the pending queue at once, so the quiz
  never waits for the network.
- About 2 s after the last answer, pending events are POSTed (up to 500 per request)
  to `/soccer-teams/api/stats/events`. The server reads the file, unions the events,
  and writes it atomically (temp file + rename). The handler is synchronous, so two
  requests can't interleave. The response is the merged file, which is how answers
  from other devices arrive. On load the app also GETs `/soccer-teams/api/data/stats`.
- Failures (offline, 4xx/5xx) keep the queue and retry after 5 s, 15 s, then every
  60 s, plus on the browser `online` event. The queue survives reloads.
- On `pagehide` / tab hidden, pending events are sent again with `fetch(keepalive)`.
  Duplicates are harmless.
- Migration: on the first load with this version (no `events:v2` key yet), the old
  `soccer-teams:stats:v1` entries become one `baseline` event per team and upload
  like answers. Their ids are fixed per device and slug, so they can't be counted twice.
  v1 kept only counts and the last 5 answers, so baselines carry no exact miss times:
  `lastWrongAt` is the v1 `lastSeen` if the last answer was a miss.

### Schedule (`reviewState`)

Every team has a due time, computed from its stats each time (nothing extra is
stored):

| Team | Due |
| --- | --- |
| never answered | now |
| never missed (`misses == 0`), `gots` = 1 / 2 / 3+ | last correct answer (`lastGotAt`) + 30 / 60 / 90 days |
| missed at least once, `streak` = 0 / 1 / 2 / 3 / 4 | last answer (`lastSeenAt`) + 10 min / 1 / 3 / 7 / 21 days |
| missed at least once, `streak` = 5 / 6 / 7+ (graduated) | last answer + 30 / 60 / 90 days |

`streak` is the number of "Got it" in a row since the last miss. A miss sets it
to 0, so the team is due again 10 minutes later. Once a team has been missed it
stays on the missed ladder for good (it never goes back to the never-missed table),
but after five correct answers in a row it graduates to the same 30/60/90-day
gaps. 90 days is the cap on both tables.

### Picking the next card (`drawTeam`)

1. Candidates: the teams in the country filter, minus the card just shown (unless
   it is the only team).
2. If any candidate is due (`due time <= now`), the card is a weighted random draw
   from the **due candidates only**. A team that is not due is never drawn while
   another candidate is due.
3. If no candidate is due, the card is the candidate due soonest (ties broken at
   random). The app then shows a quiet line above the card, "All caught up — next
   review in X", where X is the time until the earliest due team in the filter.
   (The note is only shown when nothing in the filter is due; if only the card just
   shown is due, the soonest other team comes up without the note.)

Weights for due teams (`teamWeight`):

```
never answered:  2
never missed:    1 + min(overdue, 2)
missed:          2 + min(overdue, 2) + 4 * 0.5 ^ (hours since lastWrongAt / 12)

overdue = (now - due time) / interval      0 when just due, 1 one whole interval late
```

| Due team | Weight |
| --- | --- |
| never answered | 2 |
| never missed, just due / 30+ days late (1 correct) | 1 / 2 |
| never missed, 60+ days late (1 correct) | 3 (cap) |
| missed, 1 hour ago (10-minute interval, so overdue capped at 2) | 2 + 2 + 3.8 = 7.8 |
| missed, 1 day ago, streak 0 | 2 + 2 + 1 = 5 |
| missed long ago, now due again on the ladder | about 2 to 4 |

Every team stays reachable: unseen teams are due at once, everything else becomes
due eventually, and when nothing is due the soonest team comes up anyway.

### Existing answers (before this schedule)

The schedule is derived from the stats `lib/history.js` already builds from the
events, so it applied to every answer recorded before the change, on the first load:

- Teams answered only correctly are **not** treated as unseen: they are due
  `lastGotAt + 30 days` (60 or 90 days with 2 or 3+ correct answers). If
  `lastGotAt` is missing, `lastSeenAt` is used.
- Missed teams use `streak`, which `deriveStats` recomputes from the events on
  every load, so it is exact for answer events. For a v1 `baseline` import the
  streak is the trailing "Got it" count of its last 5 answers (at most 5, which
  means 30 days). If a stats object has no usable `streak`, the trailing "Got it"
  count of `recent` is used.
- A team with answers but no usable time is treated as due now.

The clock (`now`) and random source are injectable, so the tests pin both. There is
no reset button. To start over, delete `data/stats.json` on the server and clear the
site data in each browser. Otherwise a browser's cached history is uploaded again.
